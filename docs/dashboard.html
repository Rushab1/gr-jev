MetaTool is a benchmark for tool selection. An example gives the model a user query and a list of tools, and the model names the tool that should handle the query.

It has 199 tools and 20,614 queries. The tools are ChatGPT plugins from OpenAI's 2023 plugin list, each with a name and a description. Each query is labelled with one tool. ChatGPT and GPT-4 generated the queries from the tool descriptions, and the MetaTool authors verified them by hand.

The repository has five test files. An example in a test file is a query, a tool list and a label. The files differ in how the tool list is built and in what the label is.

The paper scores the four tool-selection files with the Correct Selection Rate (CSR), the percentage of examples where the model selects the labelled tool. It scores tool awareness with accuracy, precision, recall and F1.

Distributions

  • Similar tools: the 5 queries of a tool get the same list. PolishTool is in its own list and in the lists of 48 other tools, 245 examples. 5 tools are only in their own list. 72 tools are in no scenario, reliability or multi-tool list.
  • Scenario: the 1,800 examples use 9 different lists, each for 100 to 300 examples. 53 of the 199 tools are in at least one of the 9. FinanceTool, PDF&URLTool, ProductSearch and TripTool are in 4 of the 9. Each of the four is in the list of 800 scenario examples and is the correct tool in 80.
  • Multi-tool: both correct tools of all 497 queries are among the 15 tools of the scenario list TopTool_top15. Each of the 15 is a correct tool in 24 to 100 multi-tool examples. In the similar-tools, scenario and multi-tool files together, the correct tool is one of the 15 in 1,432 of the 3,292 examples (43.5%). Each of the 15 is a correct tool in 89 to 168 examples, and each of the other 184 tools in 5 to 65.
  • Distractors: the reliability lists use 89 of the 199 tools, and hacktrack is in 335 of the 995. In the multi-tool lists 67 tools are distractors, and LawTool is one in 171 of the 497. select_10_tools_with_exclusion samples the tools of both files and calls random.seed(48) before every sample.

The 20,614 queries

dataset/data/all_clean_data.csv holds all 20,614 queries in two columns, Query and Tool.

The test files sample from it. The similar-tools file has five queries for each of the 199 tools, 995 in total. The reliability file has the same 995 queries with different tool lists. The scenario file has 20 queries for each tool in a list, and a tool in more than one list has the same 20 in each. Its 1,800 examples have 1,060 different queries, and 265 of them are similar-tools queries. get_query_by_tool in src/prompt/prompt_construction.py calls np.random.seed(48) before every sample. The four files with tool lists have 2,287 different queries in 4,287 examples.

In this study the file is the training data for the fine-tuned model. The test queries are rows of the file. Training on it without removing them puts test queries in the training data.

  • Rows of this file: 993 of the 995 similar-tools queries, 1,797 of the 1,800 scenario queries, and 519 of the 520 tool-awareness queries labelled yes.
  • The 520 tool-awareness queries labelled no come from Self-Instruct (Wang et al., 2022), CommonsenseQA (Talmor et al., 2019) and LIMA (Zhou et al., 2023).
  • The 497 multi-tool queries are in dataset/data/multi_tool_query_golden.json. None of them are rows of all_clean_data.csv.
  • Queries per tool: minimum 12, median 68, maximum 1,122.

List length

Tool lists in the test files have 5, 10 or 15 tools. A longer list keeps the correct tool and adds distractors.

A list built only from MetaTool's tools has at most 199. Jev's choice accepts up to 255 options, and a 255-tool list needs 56 tools from outside MetaTool.

5, 10, 15 199 255
  • Tool descriptions from other datasets differ in form. ToolBench's are API notes such as "Search by name" and "Enter Artist ID", and 960 of the 13,862 in ToolRet's copy (6.9%) are blank.
  • No label says whether a tool from outside MetaTool is incorrect for a MetaTool query.

Fixed positions

In the similar-tools file the correct tool is at position 1 in all 995 examples. In the multi-tool file the two correct tools are at positions 7 and 8 in all 497 examples.

Cause

  • Similar tools: get_10_most_sim searches for the 10 tools nearest to the correct tool's embedding. The correct tool is its own nearest neighbour, and the result is not shuffled.
  • Multi-tool: select_10_tools_with_exclusion calls random.seed(48) for every example and samples the 8 distractors. The two correct tools are appended last, and random.shuffle moves them to positions 7 and 8 every time.
  • Both functions are in src/prompt/prompt_construction.py.

Other files

  • Scenario: each position in a list has 20 examples. All queries in a scenario get the same list in the same order. The counts drop after positions 5 and 10 because 8 of the 9 lists have more than 5 tools and 1 has more than 10.
  • Reliability: the correct tool is in none of the 995 lists.

ToolBench is a benchmark for tool use with real REST APIs. It has 16,464 APIs from RapidAPI Hub, grouped into 3,451 tools, and 126,486 examples. Each example is a query generated by ChatGPT and a solution path. The test set has 1,100 queries.

A test example is a query and a list of APIs. The label is the subset of the list that the query needs, which the dataset calls the relevant APIs. A MetaTool example has one correct tool, or two in the multi-tool file.

Two later benchmarks contain the same 1,100 test queries. StableToolBench (Guo et al., 2024) keeps the 765 queries that GPT-4 Turbo, Gemini Pro and Claude 2 judged solvable, and adds a virtual API server. ToolRet (Shi et al., 2025) is a tool retrieval benchmark with 35 subsets, and one subset is the 1,100 ToolBench test queries.

This study uses StableToolBench's six test files and cites ToolBench and StableToolBench.

BFCL, the Berkeley Function Calling Leaderboard, is a benchmark for function calling. An example gives the model a user query and a list of function definitions, each with a name, a description and a parameter schema. The model answers with function calls, each a function name with parameter values, or with no call. The label is the list of correct calls, which BFCL calls the ground truth.

BFCL v4 has 13 single-turn test files with 3,641 examples, 4 multi-turn files with 800 examples and 2 agentic files with 255 examples. A single-turn example has one query. A multi-turn example has 1 to 8 turns, and its ground truth has a median of 5 to 6 function calls and at most 35. An agentic example is one question that the model answers by calling web search or memory functions.

BFCL marks each example correct or incorrect and reports accuracy for each test file. bfcl_eval/data/README.md calls the check for single-turn files AST evaluation, short for abstract syntax tree. The check compares the model's calls with the ground truth. In irrelevance and live_irrelevance the correct output has no call. In live_relevance the correct output has at least one call, and BFCL does not check whether the call is correct. In v4 the leaderboard's overall accuracy weights the agentic files at 40%, the multi-turn files at 30%, and the non-live, live and irrelevance files at 10% each.

This study uses BFCL as a test-only set. No model is trained on it. Jev's choice question returns one of up to 255 options and no parameter values. For Jev, only the choice of function can be scored.

Parameter values

A function call needs a value for each parameter. Jev selects from a list and writes no text, so it can produce a value only if the value is already written down: in the query or in the function's definition. The tables count the accepted values in the ground truth of the 10 single-turn files that have one.

  • In the query: an accepted value is in the query as text, in upper or lower case, or as a number in digits.
  • Schema: the function definition lists the values the parameter can take.
  • Left out: the ground truth accepts a call without the parameter.

Problems

  • Nothing to choose: in 1,022 of the 3,641 single-turn examples the list has one function, and it is the correct one. The task there is to write the call, which is the value of each parameter. In 185 more examples the label names every function of a longer list.
  • Parameter values: BFCL scores the whole call, and Jev writes no values. In 653 of the 2,501 single-turn examples with a ground truth, at least one value is in neither the query nor the function's definition and has to be rewritten.
  • Short lists: where a function has to be chosen, a list has 2 to 4 functions in multiple and a median of 4 in live_multiple.
  • Word overlap: the function that shares the most words with the query is the correct one in 94.2% of multiple and 70.1% of live_multiple. A random choice scores 38.4% and 30.2%.
  • Multi-turn: a turn depends on the turns before it. In multi_turn_base_0 the second turn calls cd(folder='temp'), a folder that the first turn creates.
  • Agentic: the ground truth of web_search and memory is a text answer, and no function is the label.

Position, order and list length

These experiments measure how the selection of a decision model changes when the tool list changes and the query stays the same. They run Jev and open-weight decision models. Claude is not run in them.

A run is in the plan only if it proves a claim of the paper. The simplest run that can show an effect is run first, and its result is read before the next run is added. A repeat run, a control or a second variant is added when a result needs it.

Placement of the correct tool

In every list of 5 or more tools the correct tool is placed at 5 positions: first, 25%, 50%, 75% and last. That gives 5 orders of each example. The distractors are shuffled once per example with a seed and keep that order in all 5.

In a list of N tools the 5 positions are 1 + q × (N − 1) for q = 0, 0.25, 0.5, 0.75 and 1, rounded to the nearest position, with a half rounded down. MetaTool's test files have lists of 5, 10 and 15 tools.

The adjacent pair starts at 1 + q × (N − 2). In MetaTool's multi-tool file as released, the two correct tools are adjacent at positions 7 and 8 in 497 of 497 examples. One of them is the query "I want to know the latest news about Tesla and how it has impacted the stock market.", with the correct tools NewsTool and FinanceTool.

The rule follows Baker et al. (arXiv 2412.10079). They place 2, 3 or 4 evidence documents among 20 documents: 5 placements with the evidence documents adjacent, and 3 or 4 placements with distractor documents between them. They report higher scores when the evidence documents are adjacent. The same rule is used for MetaTool, ToolBench and BFCL.

For a multi-tool example Jev's answer is the two tools with the highest probabilities of one question. The example is correct when they are the two correct tools. When several tools share the second-highest probability, Jev has named no second tool. That counts as a miss, and these cases are counted.

Rotating the list was considered and dropped. A rotation puts every tool at every position once, and a list of 199 tools would need 199 orders.

The CSR figures of the MetaTool paper on the three single-tool files were measured with the answer "None" allowed. Without the candidate, Jev selects among 10 tools, and the published task is a choice among 10 tools and "None". baibizhe/jev-decision-benchmarks gives Jev the tool list plus "None" on the single-tool examples.

The reliability file measures how often a model answers "None" when no tool is correct. With "None" in the lists that have a correct tool, the runs also measure how often it answers "None" when a correct tool is in the list. A model that answers "None" in 90% of its answers, whatever the list, scores 90% on reliability. On similar tools with "None" offered it scores at most 10%. With "None" left out of similar tools, the 90% has no visible cost.

Similar tools and reliability use the same 995 queries. With "None" in both, each query is tested with the correct tool present and absent, on the same 11 candidates. A caller does not know in advance whether the correct tool is in the list.

Two rules were considered and dropped. The first is "None" in every list of every dataset: MetaTool's multi-tool prompt asks for two tools, and StableToolBench has no example without a relevant API, and results on them would not be comparable with published results. The second is "None" only in the lists that have no correct tool. Jev's requests are independent and Jev learns nothing between them, and the candidate's presence gives nothing away to it. The rule is dropped for the false "None" answers it would leave unmeasured.

"None" is always the last candidate, and no run puts it first. Similar tools and reliability use the same 995 queries, with "None" last in both. A model that selects "None" for being last would also select it on similar tools, where it is wrong, and the first run shows that share.

Released order

Every example is also run once with its tool list in the released order, and a multi-tool example once with each wording. On MetaTool that is 4,784 tool lists: 995 similar tools, 1,800 scenario, 995 reliability and 994 multi-tool, 497 with each wording.

Published results on MetaTool use the released order: the MetaTool paper, PA-Tool (arXiv 2510.07248) and baibizhe/jev-decision-benchmarks. The placement runs reorder the lists, and their results are not comparable with those. The released-order run gives the row that is comparable, and the placement runs are compared against it.

The prompt still differs from the MetaTool paper's. Jev receives the query as the state and the tools as candidates. The released prompts of the three single-tool files hold 5 worked examples.

The score is the plain CSR: the percentage of examples with a correct selection, as published results on MetaTool compute it.

The similar-tools file has 199 different tool lists, the scenario file has 9, and the multi-tool file has 15 different correct tools. Confidently wrong answers

A confidently wrong answer is a wrong selection to which Jev gives a high probability. A rule that accepts Jev's answer when its probability is high accepts these answers, and no other model checks them. They are measured in every Jev run.

MeasureDefinition
Error rate of confident answersOf the answers whose top probability is at or above a threshold, the share that are wrong
Confident share of errorsOf the wrong answers, the share whose top probability is at or above the threshold
AUROC of the top probabilityHow well the top probability separates Jev's wrong answers from its correct ones

Each is reported by position of the correct tool, by list length and by test file. On the reliability file, where no tool is correct, a confidently wrong answer is a tool selected with a high probability.

The three measures are the ones in arXiv 2609.26550, which uses Jev to judge pairs of model outputs. At a top probability of 0.9 or more it reports a Jev error rate of 2.1% on RewardBench (24 of 1,155 judgments) and 6.5% on JudgeBench (9 of 138). Those errors are 21% and 12% of Jev's errors, against 41% and 25% for GPT-6. On RM-Bench the error rate at 0.9 or more rises from 1.5% on easy pairs to 7.9% on style-adversarial pairs.

kachar/jev-tool-search reports that with 199 tools every change of answer between two orders occurred when a top probability was under 0.6.

The top probability depends on the number of tools. TypeSafe's documentation says 0.5 "is a weak answer among two options and a strong one among ten". Jev also returns a confidence, equal to (top probability − 1/n) / (1 − 1/n) for n tools. Both are saved with every answer.

Accept or escalate

Jev selects first. When its top probability is at or above a threshold, the selection is final. Otherwise a frontier LLM, Claude Sonnet 5 or Claude Opus 5, selects on its own. Claude gets one call per example here and no call in the position runs.

The rule is from arXiv 2609.26550. It picks the threshold on about 100 labelled examples from the grid 0.5, 0.6, 0.7, 0.8, 0.9, 0.95 and 0.99: the lowest threshold whose accuracy stays within 2 points of the stronger model, by a one-sided 95% lower bound. The threshold is fixed before the test examples are run.

Jev as a co-pilot

Question: can Jev reduce the token cost of a frontier LLM on difficult tasks? The frontier LLM proposes each function call, and Jev checks the choice of function before the call runs. A wrong call caught at that point does not cost the tokens of the steps that recover from it. The trajectory corrects itself.

Jev and the frontier LLM select the function on the same examples. Each example falls into one of four outcomes.

OutcomeFor a co-pilot
Both correctNothing to correct
Only the LLM wrongAn error Jev can catch
Only Jev wrongA false alarm
Both wrongAn error Jev cannot catch. Recorded with whether both select the same wrong function.

This is a parallel study to REFLEX (arXiv 2609.26532). In REFLEX, Jev decides first and a strong LLM is called when Jev's confidence is low or text has to be generated. It reports 72.7% fewer strong-model calls on a 100-task benchmark and limited advantage on BFCL.
